## 工作包 1：OS4.0.4 触摸启动结论（P0）

**已知事实：**用户曾报告最新 OS4 镜像没有触摸上报；已有日志显示触摸模块、输入节点和手动 raw0 后的事件证据。自动启动候选的控制器响应、事件进入 GUI 和唤醒仍没有当前候选的完整证据。

**只做一次：**对现有日志、设备树、固件加载路径和当前候选的启动顺序进行定向判断。找到明确的软件缺陷时，维护一个补丁，运行受影响的离线回归并构建；找不到软件缺陷时，记录“软件路径未发现可修复点，剩余为硬件边界”，关闭调查。

**完成条件：**有明确的修复结果或明确的未验证结论；不再因为 raw0、等价输入回放或已有报告哈希变化重复建立测试。

## 工作包 2：容量刷新页面卡住（P1）

**已知事实：**现有采集显示刷新后台约 5.15 秒完成；长时间采样时显示提交线程在 `dpu_kms_wait_for_hw_cfg_done` 的 D 状态等待，Recovery 主线程也在 DRM atomic commit 附近。没有第二个相邻采样或软件错误返回证据。

**只做一次：**基于现有 `refresh-stuck` 日志和 GUI/DRM 调用链判断是软件生命周期问题，还是只能归入 DPU/DRM 硬件等待。只有前者才改代码；后者写入限制并停止。

**完成条件：**补丁及定向回归，或有证据支撑的“无法从 Recovery 软件侧修复”结论。禁止重采同一现场、重跑相同 worker/DONE 夹具或凭一个 D 状态直接修改 DRM。

## 交付规则

生产修改必须通过维护的设备树补丁进入源码；最终构建顺序为 `installclean` 后 `make -j$(nproc)`。每个连贯修改批次只同步一次 GitHub：

```bash
python3 scripts/sync_github.py --push --message "describe the actual change"
```

同步前核对公开仓库不包含镜像、编译产物、原厂固件、私钥、原始设备日志、缓存或凭据；远端分支必须等于本地提交后才能报告完成。

三个工作包全部收尾后，目标从“适配开发”转为“维护模式”。历史十二组分类只用于查找证据，不再作为自动生成任务的清单。
