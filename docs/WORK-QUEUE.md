## 工作包 1：OS4.0.4 触摸启动结论（P0）——已收尾

**已知事实：**用户曾报告最新 OS4 镜像没有触摸上报；已有日志显示触摸模块、输入节点和手动 raw0 后的事件证据。自动启动候选的控制器响应、事件进入 GUI 和唤醒仍没有当前候选的完整证据。

**结论：**对现有日志、设备树、固件加载路径和当前候选启动顺序完成了一次定向判断，没有发现可以确认的 Recovery 软件缺陷，因此没有新增补丁，也没有重编镜像。当前候选的 exact-profile 路径明确先执行 `cache`：校验并写入 `/lib/firmware`、设置 firmware search path、建立 `cached` 标记；随后才执行 `modules` 加载 `synaptics_tcm2`；模块阶段结束后才执行 `dijun-touch-reports.sh`。该脚本还检查模块 `live`、`Xiaomi_Touch_Input_0` 注册、写入 `enable_touch_raw=0` 及读回值。

当前候选的 ramdisk 顺序检查已完成，名称与 SHA-256 以[交付报告](../simulation-report.md)为准。现有 9 项策略和镜像打包证据只证明软件流程与节点边界，不证明控制器接受请求或产生真实事件。

用户提供的旧日志中出现的固件加载失败和无事件，不能直接转移为当前候选仍存在同一顺序错误；当前离线证据也不能证明 OS4.0.4 控制器响应、Linux 事件进入 GUI 或唤醒延迟。

**完成条件：**已形成“软件路径未发现可确认修复点，控制器响应/实机事件仍未验证”的结论。本工作包关闭；除非出现新的触摸故障日志或直接回归证据，不再因为 `raw0`、等价输入回放或报告哈希变化重复建立测试。

## 工作包 2：容量刷新页面卡住（P1）——调查收尾，未宣称修复

**已知事实：**现有采集显示刷新后台约 5.15 秒完成；长时间采样时显示提交线程在 `dpu_kms_wait_for_hw_cfg_done` 的 D 状态等待，Recovery 主线程也在 DRM atomic commit 附近。没有第二个相邻采样或软件错误返回证据。

**处置：**现有采集摘要一致，当前 worker DONE 发布、页面终态映射和 GUI tick → 显示提交顺序已对照。没有确认新的 Recovery 生命周期缺陷；显示 ioctl 等待会阻止后续 tick，但这不证明现场持续卡死或硬件是唯一根因。本轮不修改代码、不重跑历史 worker/DONE/主循环夹具、不重新构建，见[最终判断](REFRESH-STUCK-INVESTIGATION.md)。

**结束条件已满足：**基于现有材料无法确认可从 Recovery 软件侧修复的根因，记录为“现场未定位、离线调查结束”。仅新的区分性现场证据或直接代码回归可重开；不要求用户重采。

## 交付规则

生产修改必须通过维护的设备树补丁进入源码；最终构建顺序为 `installclean` 后 `make -j$(nproc)`。每个连贯修改批次只同步一次 GitHub：

```bash
python3 scripts/sync_github.py --push --message "describe the actual change"
```

同步前核对公开仓库不包含镜像、编译产物、原厂固件、私钥、原始设备日志、缓存或凭据；远端分支必须等于本地提交后才能报告完成。

本轮离线执行已收尾。仍有 **1 项未定位现场故障（容量刷新画面）**；自动触摸、硬件解密、USB、真实 OTA/合并等未验证，以及 CLI 退出状态等未实现边界，均在[兼容矩阵](../compatibility-matrix.md)保留。它们不被改写为成功，也不继续自动拆成任务。后续仅按新故障、直接回归或用户明确指定的新增功能建立有限任务。
